# One-time Appwrite migration notice

Campaign `contentos-appwrite-signin-update-20260912-v1` uses the existing production Resend key and sender `ContentOS <support@getcontentos.co>`. Its fixed content links to https://getcontentos.co/login. No new service, schedule or billing configuration is needed.

The owner-only preparation script stages the original migration inventory in private `contentos_app.migration_mail_campaign` and `migration_mail_recipient` tables. It records test/disabled/deleted/duplicate exclusions, snapshots email addresses, and refuses to overwrite an existing campaign. Source inventories and operator tokens must remain outside the repository in restricted files. Runtime grants allow result updates only: they cannot insert recipients, change addresses/content, or delete the ledger. Auth, profiles and entitlements are read-only throughout this process.

The production-only POST route `/api/internal/migration-email` requires a separate 256-bit operator token whose SHA-256 hash is stored in the campaign. It expires after two hours. The route accepts only status, send-one and verify actions; recipient lists and content cannot be supplied through HTTP. Responses return aggregate counts, never member details or secrets. Requests must carry the token in the Authorization header, never in a URL.

`node scripts/migrations/run-migration-email.mjs <private-token-file> status|send|verify` operates only on the fixed production host. The sender rechecks account existence, disabled status and unchanged email before each reservation, observes existing daily/monthly mail caps, and persists provider ID and timestamps. A transaction serializes reservations; account and normalized-email unique indexes prevent duplicates. Each provider retry uses identical content and the same stable idempotency key, at most three attempts for network errors, HTTP 429 or 5xx. No sent, skipped or failed row can reopen; interrupted sending rows require reconciliation and are never automatically retried by a subsequent run. This avoids reliance on Resend's 24-hour idempotency retention. Successful completion closes the campaign permanently.

A 'sent' ledger result means Resend accepted the message. `verify` separately records Resend's last delivery event; delivery and inbox reading are different states. A failed/ambiguous result must be reconciled against Resend before any future recovery work. Never clear the ledger or change the campaign ID to force a resend.

Validation: unit tests cover content, operator authorization, bounded retries and storage failures. The isolated test database exercises concurrent sends, reruns, terminal-state protection, restricted runtime privileges and unchanged user/authentication data with a mocked provider. Production verification uses real send IDs and a second run that must send zero messages.
