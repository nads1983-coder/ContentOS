# PR 22: subscription period reconciliation — 10 November 2026

## Root cause and fix

The Stripe API version pinned by the application (`2026-02-25.clover`) returned the billing period on the subscription item. The existing mapper read only the older top-level `current_period_end`; Checkout completion, subscription webhooks and dashboard/Studio reconciliation all use that mapper, so the profile stored a null end and usage fell back to a calendar window.

The mapper now accepts valid start/end timestamps from the single unambiguous subscription item, while retaining legacy top-level end support. Missing, incomplete, malformed, reversed or ambiguous item periods are not used. The start and end are stored in the existing profile JSON; no schema migration is introduced. For the same subscription, missing dates and older end dates do not erase or roll back known boundaries, and an end-only response for the same period cannot erase its known start. Current Stripe retrieval remains authoritative for webhook reconciliation. Immediate Clover cancellation is not reactivated merely because the item period ends in the future.

Generation, image quota, Dashboard and Studio usage windows use the recorded start and end. An existing active subscription receiving its first period-start backfill retains the previous usage-window start until that verified Stripe period ends; the transition survives extension of the same period and is cleared on renewal. This protects existing usage counters from an early reset in either direction of calendar-to-billing alignment. Legacy inferred month calculations clamp month-end dates. Prepaid credits remain in the separate ledger and are not reset or granted by this change.
