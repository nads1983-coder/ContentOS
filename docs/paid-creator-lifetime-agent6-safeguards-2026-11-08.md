## Administrator reinstatement

`POST /api/admin/lifetime/reinstate` requires a verified session, an email in `ADMIN_EMAILS`, same-origin write checks, fulfillment enabled, a purchase UUID and a 10–500 character reason. Its body is streamed with a 2 KB/5 second limit. The gate is currently off. It fetches the stored Session and PaymentIntent server-side and checks the account, purchase, attempt, price, amount, currency, status and charge. A partial refund must be less than the total. It fetches the complete dispute list (fails closed if Stripe reports more than 100) and requires **every** matching dispute to be won. An active Creator/Lite subscription requires separate reconciliation; Studio is preserved. No fully refunded purchase or lost/open dispute may be approved.

Before Stripe reads it snapshots recorded reversal evidence; under the same advisory lock used by fulfillment it locks the purchase, compares the exact evidence set again, locks the profile and inserts an append-only `paid_lifetime_adjudications` row with administrator ID/email, reason, time, purchase, charge, dispute IDs and reviewed event IDs. Then it changes only the separate paid lifetime status and purchase status. Existing subscription identifiers and other fields are retained. Runtime can select/insert decisions but cannot update/delete them.

Risk evaluation excludes the exact event IDs covered by a valid recorded decision; full-refund evidence is **never** excluded. Previously seen duplicate webhook events and ordinary reconciliation therefore do not undo a decision. A new, previously unseen reversal event always remains actionable, even if it turns out to be a delayed event for an earlier won dispute; this conservative choice may require another administrator review. A new full refund revokes access. A refund arriving during Stripe verification changes the evidence snapshot or locked status and rejects the stale approval. If Stripe is unavailable, identity/amount is ambiguous, a full refund exists, a dispute is open/lost, or a list is incomplete, approval fails closed. There is no automatic reinstatement.

During the resumed review an additional snapshot race was fixed: a fresh disputed Stripe snapshot now records distinct evidence even after an earlier approval, and webhook and reconciliation callers read the immutable decision revision before fetching Stripe. If an administrator decision intervenes, fulfillment returns `stale_snapshot` and the caller retries with a fresh provider read. The local PostgreSQL test checks both an outdated observation and a later new dispute. The check is not a substitute for live test-mode dispute validation.

Partial refunds retain already-active access pending review; if a partial refund arrived before activation the purchase remains in review until an explicit approved decision. A full refund and a dispute take precedence. Lost disputes remain revoked. The admin endpoint returns generic errors and does not expose Stripe secrets. Tests use synthetic Stripe objects: actual Stripe API shape, webhook ordering, account/mode isolation, late events and duplicate delivery **must still be tested with real test-mode Stripe**. This API is not an administrator UI; `ADMIN_EMAILS` governance, reviewer identity, support procedures, notices and response times still need owner review. Do not expose or operate it in live mode before independent verification.

## Shared-budget fairness and customer impact

`lib/commercial-ledger.ts` implements an opt-in per-account admission limit across text and image provider spend, configured by `AI_ACCOUNT_MONTHLY_CAP_MICROGBP`. **It is unset by default and is not currently enforced.** A concrete candidate tested in isolation is £7.50 per London calendar month (25% of the unchanged £30 global cap); adopting it requires the founder’s explicit approval because the request prohibits changing spending limits without approval. If approved and configured, the share includes settled conservative estimates, pending holds and uncertainty; released pre-dispatch calls free their hold. The global advisory lock serializes both account and global checks. A request reserved before midnight is checked again against both caps when dispatched in the new month. Same-account concurrent text and image requests cannot bypass it when configured, and the existing API routes use this ledger when they call the AI provider. No application-level control can constrain another service or direct use of the provider key outside the ledger.

If configured, this is a **material new capacity policy affecting existing Free, Lite, Creator, Founder and Studio accounts**, not a change to their numeric plan credits. It can deny further AI requests until the next budget month even if credits remain, including existing subscribers. The message says capacity is temporarily unavailable and their credits/content remain unchanged. At the GPT-5.2 maximum reserve (£0.680602), 11 simultaneous maximum holds total £7.486622; a twelfth is refused for that account. Settlement below the reserve releases room. At actual settled cost near the maximum, the share can prevent a customer from using 50 generations in that month. The limit remains unset pending explicit founder approval of the proposed 25% choice, customer messaging and impact **before any deployment or merge**; it is not a claim that the offer is fully funded or deliverable. The account share is not an identity-level guarantee against multiple accounts, and whichever eligible account consumes the final remaining global funds can still exhaust that remainder. Historical opening-balance spend has no account attribution and is counted globally, not against a particular user.

**Current limitation:** with the per-account setting unset, individual account monetary fairness is not enforced. No additional success promise is made: `assertLifetimeCapacity` still protects all incumbent £30 and permits zero lifetime commitments. The £30 cap blocks admitted application spend, it does not provide money for every sold entitlement, cover usage outside the ledger, or reconcile provider invoices.

## Financial reporting

`GET /api/admin/ai-financial-report` requires the same authenticated `ADMIN_EMAILS` authorization, uses a consistent read-only PostgreSQL snapshot and returns no-store aggregate data. It reports delivered text/image generation counts, distinct accounts with spend requests, provider-reported token counts, usage-derived **estimated** settled micro-pounds, reserved/dispatched/uncertain holds, average estimated settled cost per generating account, £30 global utilization, applicable opening balance, global headroom and additional funded lifetime places. It explicitly says provider-invoice actuals are unavailable; provider token counts are not an invoice.

`customer_cohort` is captured at admission: lifetime Creator primary, active recurring subscription (including a current paid Studio overriding Creator lifetime), or other. Founder and owner/complimentary rights remain separate, not silently labeled as the new paid lifetime offer. `0008_ai_spend_cohort.sql` labels older records `unknown` because historical plan transitions cannot safely be reconstructed. One user can appear in different cohorts if they changed plans during the month; counts are distinct within each cohort, not additive unique customer totals. This is operational reporting, not a revenue, VAT, tax, provider bill or accrual ledger. Confirm Stripe/OpenAI invoices separately.

Historical read-only evidence from the original audit on 8 November recorded £0.475409 application-accounted November spend over 17 requests: 12 GPT-4.1 text requests (£0.147053) and 5 image requests (£0.328356). It is a dated ledger snapshot, not current invoice actuals or proof of today's model override. No new production data was queried here.

## Durable reconciliation and operational visibility

`0007_lifetime_reconciliation_jobs.sql` adds jobs, durable alerts and append-only administrator retry actions. The worker seeds at most 50 untracked jobs per category, claims one due job at a time using `FOR UPDATE SKIP LOCKED`, a unique lease token and a 40-second expiring lease; late workers cannot overwrite a subsequently claimed job. It processes at most 10 guards and 50 purchases per invocation, limits Stripe calls with 6/20 second abort budgets, and rotates due work by `next_attempt_at`/ID. Database execution is subject to its own statement timeout; these are **not** hard end-to-end wall-clock guarantees.

Failures retain the purchase/slot, persist a sanitized error code and use exponential 30/60/120/240/480/960/1920/3600-second backoff capped at one hour. The eighth failure moves the job to `attention` and writes a durable `retry_limit` alert; a worker killed on its eighth leased attempt is recovered after lease expiry. Normal open/unpaid sessions are rescheduled in five minutes without consuming the failure budget; completed purchases are rechecked daily. Repeated failures never create a new Stripe idempotency key or release an uncertain slot. The next worker pass repairs an alert missing after a crash between state and alert persistence.

`GET /api/admin/lifetime/reconciliation` gives administrators up to 100 failed/attention jobs, alerts with current job state, unresolved review/disputed purchases and unmatched payment events (some unmatched events can belong to unrelated Stripe products). `POST` with `{kind,id,reason}` explicitly requeues an unleased attention job and records an immutable administrator action; it never changes a purchase, payment or entitlement. The view is bounded and has no pagination/UI. Alerts are durable, visible and actionable, but **there is no configured push/page/email or dashboard**: an owner must arrange protected polling/monitoring and alert delivery before relying on them. Queue seeding, leases, webhook replay and Stripe paging still need load, multi-instance, clock and real-provider verification. Long Stripe search without a durable pagination cursor can repeatedly time out and exhaust retries, requiring admin review. Concurrent work remains idempotent rather than exactly once.

The repository's Vercel cron is once daily at 04:00 UTC. The 30-second-to-one-hour values are earliest retry times, not execution guarantees; normal five-minute reschedules also wait for the next invocation. An independently authorised, appropriately frequent scheduler and monitored alert delivery must be configured and tested before reliance on this worker. No external scheduler was configured here.
