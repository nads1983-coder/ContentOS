## Implemented

1. **Partial refund:** `lib/paid-lifetime-fulfillment.ts` durably records `review`, preserving already-active access. Review received before activation cannot grant access; replay cannot auto-reinstate; existing full refund/dispute takes priority over later partial review. PostgreSQL and unit tests cover active, pre-activation, replay and escalation to full refund. The inbox record is the review marker: there is no administrator queue or resolution mechanism yet. Existing review reasons also take this path if the purchase is already active; assess all future review event types before adding them.
2. **Reconciliation:** `lib/paid-lifetime-reconciliation.ts` rotates recurring guards by durable `checked_at` before Stripe work, checks up to 10 guards, limits the guard Stripe phase to six seconds and passes a 20-second abort signal to Stripe requests for the overall run. Lifetime rows rotate before external work so interrupted attempts are revisited later. Batches remain bounded (50 lifetime rows). Uncertainty, failed guard checks and timeout return counters and structured warning logs, without customer identifiers. Existing uncertain payment holds are not freed on timeout.
3. **Stripe read transport:** `lib/stripe-rest.ts` propagates optional abort signals to Checkout, subscription and PI reads and paginated lost-session searches; other callers retain the existing 12-second request timeout. A test confirms a pre-aborted search makes no Stripe call.
4. **Migration:** journaled `0005_lifetime_guard_reconciliation.sql` adds `checked_at` and its column-scoped runtime grant; it does not modify previously committed 0004. Actual runner tested from production-shaped 0000–0002 journal plus existing external 0003, including induced 0004 rollback, applying 0004 first, upgrading to 0005, safe repeated run, grants, data preservation and concurrency. No production migration was run.

## Material limitations of these changes

- A 20-second Stripe abort budget is **not a hard end-to-end execution limit**: database calls, parsing and fulfillment transactions do not accept its abort signal and each DB call has its own timeout. Rotation-before-work improves recovery but is not a leased, exactly-once queue; overlapping worker invocations can duplicate reads. Pagination has no durable cursor, so a large list may restart after each deadline and require manual reconciliation. `console.warn` and response counters are not a delivered alert or durable retry queue; monitoring/alert routing, retries and an operator dashboard remain unimplemented. Production cron secret, scheduler, Stripe timeout and interruption behaviour remain unverified.
- A durable administrator **reinstatement workflow has not been implemented**. The current event inbox treats historical dispute/refund evidence as permanent; simply editing a profile would be undone on replay. A safe implementation must use authenticated authorization, a durable adjudication record identifying the exact historical event set and independently fetched Stripe outcome, transaction serialization, protection against new reversals arriving after review, replay/idempotency tests and documented operator procedures. Winning a dispute alone never auto-restores. Founder decisions are needed on reviewer authority, partial-refund remedy, response time, repeat purchases and support. Do not delete the inbox or promise reinstatement before this exists.
- Full refunds and disputed purchases revoke lifetime access. Existing handling records every dispute lifecycle event as disputed, including won; it does not yet distinguish final lost versus won for a review queue. Stripe's actual partial/full/dispute payloads and event ordering remain unverified in test mode.
- Per-account spending fairness and lifetime/subscription financial reporting have **not** been added. Existing server-side attempt throttles (20/minute, 100/day), pending-request limits, generation quotas and shared global monetary lock reduce abuse but do not ensure fairness: a single customer can consume the remaining £30. The ledger shares spending across all tiers and does not provide a reliable commercial cohort classification in its stored request rows. A partition/fair-share policy requires a documented design protecting existing customers and must not reduce their entitlements. Existing generic temporary-capacity response preserves unused credits.
- Monitoring logs require an independently configured operational sink, thresholds and alert delivery. These were not configured. Agent 4's other findings about expected Stripe account/mode, old/unlinked subscription Checkouts and asynchronous-failure terminal semantics still require design and real sandbox testing.
