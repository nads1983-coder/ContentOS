Several flags are over-conservative evidence matching. `lib/business-facts.ts` accepts complete, matching source sentences and very specific paraphrases. Given a source sentence `Tickets cost £12`, an isolated check accepts that exact claim, rejects `Tickets are £12`, and also rejects an altered `Tickets cost £13`. The latter rejection is required. Similar rephrasings of the explicitly supplied £5 option and 1,000 newsletter subscribers are rejected. The milestone helper in `lib/claim-evidence.ts` uses deliberately restrictive patterns for subject, quantity and unit, and does not generally resolve arbitrary named-business/channel paraphrases. This is a grounding/evidence-matching limitation, not evidence of an output token failure.

Other flags cannot safely be dismissed as false positives. Examples include newly promised future updates, a changed event timing such as `just`, and provider-generated repair-service commitments that the brief did not establish. Full outputs can contain both supported and unsupported claims. Formatting is separately relevant: some outputs represent several Instagram alternatives as separate sections, but the observed exceptions occur earlier in publication preparation; this diagnosis does not prove those outputs would pass later format/quality checks.

A safe remediation requires narrow relational evidence rules and adversarial tests that retain subject, currency, amount, event, negation, qualifications, timing and scope. Never approve a sentence merely because it contains a source amount, or weaken the validator to raise a score. Rerun existing grounding/hashtag baselines and representative real API cases after the correction, then perform blinded quality review and test bounded retries.
