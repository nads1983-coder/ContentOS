# AI pricing review runbook

The pricing policy is a bounded review of provider rates, not the monthly funding approval. It expires at 00:00 UTC on 19 December 2026. Requests during the final seven days emit `AI pricing policy requires review before expiry` in server logs. This warning requires an operator to monitor logs; it is not an external alert and cannot warn during periods with no requests. Schedule a review before 12 December.

Before renewal, check the current provider prices and model availability, exchange-rate contingency, payload/token bounds, reserved and actual spending, and compare them with the rates in `lib/ai-cost.ts`. Review all supported image models, including shutdown restrictions. If bounds remain conservative, update the policy version and expiry and run `node --test tests/commercial-cost.test.mjs` and the disposable PostgreSQL ledger suite. Submit a reviewed deployment; expiry does not renew automatically. If pricing cannot be verified, keep the existing fail-closed behaviour.

`pricing_review_required` means the rate policy requires review; `global_capacity_exhausted` means the £30 monthly ledger cannot fund the request. Neither authorises a budget increase. The database funding configuration and advisory lock remain mandatory and are not modified by a policy renewal. Roll back using the prior production deployment; after the old deadline that rollback will fail closed.

## Image-bound investigation and overrun accounting

The actual Image API request is one non-streaming `high` quality opaque PNG, with size `1024x1024`, `1024x1536` or `1536x1024`, text prompt only, no image input or partial images. The request uses a single `fetch` with no automatic retry; failed or uncertain dispatched calls retain their reservation, and the same request ID cannot be dispatched twice. Application admission uses a PostgreSQL advisory transaction lock and includes outstanding reservations in the shared £30 limit. OpenAI's [Image API reference](https://developers.openai.com/api/reference/resources/images/methods/generate) does not document a max-output-token parameter for image generation. Its [calculator](https://developers.openai.com/api/docs/guides/image-generation) describes output estimates, not guaranteed maxima.

With the existing 16,000-byte input limit, the theoretical quote maximum for Flare is £0.345576 (20,096 input-bound units at $5/million plus 6,250 output tokens at $30/million, multiplied by £1.20/USD); Image 1.5 is £0.360576 at $32/million. These are application reservations, **not confirmed maximum provider charges**. Image 1 has been shut down and the application rejects new requests. No billable API calls were made to establish a maximum.

The ledger now records measurable provider usage above the quoted bound, conservatively rates unexpected image-input tokens, retains at least the previous accounted amount, marks the request uncertain and suspends further admissions in the same transaction. A repeated overrun event cannot lower or duplicate the amount. Invalid or unrepresentable usage remains reserved and suspended for manual reconciliation. This improves accounting after the fact; it does not prevent one unbounded request or concurrent already-dispatched requests exceeding £30. A separately monitored provider-level project spending limit may mitigate exposure but must not be assumed to stop in-flight calls exactly at the threshold.

The local disposable PostgreSQL suite passed 13 synthetic scenarios, including concurrent final admissions, exhaustion, retry/deduplication, failed requests, normal text/image settlement and the new overrun-persistence test. The local harness was a temporary adaptation of the existing remote-guarded test and used mocked provider responses; its inherited `real Neon` label was inaccurate. Tests of actual provider usage or an enforceable output cap were not performed. Pricing-policy and image unit tests, TypeScript and lint are run separately as described in the PR.

**Release remains NOT READY:** obtain a documented enforceable per-request charge bound from the provider or an independently funded/approved containment plan. Options for founder decision include an isolated provider project with a reviewed spending limit and explicit residual in-flight risk, or temporarily suspending AI image requests while preserving existing text access and customer entitlements; the latter changes customer experience and requires approval. Do not silently change model, quality, limits, entitlements or budget. Any provider project cap must be validated for actual cutoff semantics. If a bounded solution is approved, rerun verification, merge only this maintenance PR, monitor spending and suspension alerts, and retain the previous deployment for rollback. Rolling back after 19 November restores the expired fail-closed policy and removes the overrun-accounting correction.

## Isolated image project investigation — 10 November 2026

The founder selected a separate image budget, keeping the total at £30. OpenAI supports project-level monthly spend limits and an optional **Enforce a hard limit** switch: a threshold with only an alert is advisory. OpenAI states that enforcement is not instantaneous and recorded spending can slightly exceed a hard limit, without specifying a numerical bound or a guaranteed treatment of already-dispatched calls. [OpenAI project controls](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform), [spend-limit troubleshooting](https://help.openai.com/en/articles/6614457-why-am-i-getting-an-error-message-stating-that-i-ve-reached-my-usage-limit). The documentation reviewed does not guarantee a maximum delay or maximum single image charge. Consequently neither a project hard limit nor the existing reservation demonstrates a strict £30 worst-case ceiling; the maximum overshoot in pounds remains unquantified. Do not infer that an alert or delayed project usage report is an instantaneous kill switch.

The authorised browser reached the OpenAI sign-in page, so this session did not verify account-specific project permissions, configured limits or enforcement. No project, key, spend limit, routing, allocation or environment setting was created or changed. Following the instruction to stop when a defensible boundary cannot be established, no allocation feature was activated or implemented, and no image suspension was introduced. The PR's existing shared ledger and post-call overrun suspension are not a text/image partition and cannot prevent image requests from exhausting text funding; earlier in-flight requests may still incur cost after suspension.

For discussion only, a provisional £24 text / £4 image / £2 contingency division sums to £30, but is **not recommended for activation yet**: November's last observed ledger sample had only 11 delivered text requests (£0.135716) and five delivered images (£0.328356), plus three undelivered text requests (£0.035258). The sample is too small to establish subscriber demand, peak usage or sufficient paid-customer capacity. The full £2 contingency is not a provider-enforced buffer, and the £4 image allocation would admit at most 11 simultaneous maximum-size Flare reservations at the current £0.345576 quote if otherwise empty; this is not a maximum of actual provider charges. A production deployment must first establish the complete month-to-date provider bill, other project consumers, customer demand and a guaranteed or explicitly approved residual-risk boundary, then obtain founder approval for the allocation.

The existing 52 cost/image unit tests, TypeScript and lint were rerun, as was the 13-scenario disposable local PostgreSQL suite with mocked provider responses. This verifies the current shared-ledger safeguards, **not** isolated image-budget enforcement, delayed provider billing reconciliation, or text continuation after an image sub-budget is exhausted. Those features do not exist yet. The local harness was a temporary adaptation as described above; the `real Neon` output label does not reflect its localhost connection. No production database was used for these integration tests.

**NOT READY.** Before implementation or launch, obtain OpenAI's account-specific written upper-bound/cutoff semantics or founder approval of a precisely quantified residual-risk plan; determine how to preserve a separate text reserve while charging measured and uncertain image usage; verify safe secret provisioning and project isolation; and test all budget/concurrency scenarios in a disposable environment. Do not merge or deploy this PR as an image-budget solution. The prior deployment remains the rollback option, with the earlier documented 19 November fail-closed deadline.

## Controlled-risk preparation — 10 November 2026

This section supersedes the earlier statement that no allocation feature was implemented. An **inactive-by-default** application split is prepared behind `CONTENTOS_AI_BUDGET_SPLIT=approved-v1`. No value was set in any deployed environment. When explicitly enabled it caps new text reservations at £24/month and image reservations at £4/month; the remaining £2 is unavailable contingency, and the existing £30 global check remains in force. The limits include accounted reservations and are checked under the same database advisory transaction lock. Any other nonempty setting fails closed. No migration, allowance or model change is included.

While enabled, one image reservation or dispatched request blocks all further image admissions, and any uncertain image charge blocks further image admissions even across months until a qualified operator reconciles it. This intentionally fails closed after crashes or uncertain provider calls and can require manual recovery; do not delete a financial record or clear uncertainty without verified provider billing evidence. Text can continue against its allocation after image exhaustion or ordinary uncertainty. A measured provider-bound violation still suspends **all** admissions, retaining the stronger existing safeguard. Image requests have no automatic retry. Uncategorised opening balance blocks image allocation in its opening month; text is conservatively charged the full opening amount. The existing global ledger is retained and no external provider bill is silently treated as reconciled.

Only the existing ledger can enforce this split. During a rolling deployment, older instances that do not understand it could bypass the new partition; reconcile existing outstanding requests and drain all old versions before any approved activation. Never activate by setting the flag until the founder approves the allocation and demand/funding evidence is reviewed. Changes to the flag are production configuration changes and are not included in this PR's automatic release. A separate image OpenAI project and credential have not been created or configured. A provider spend limit can supplement but not replace the application guard; OpenAI documents a delayed enforcement window and does not publish an upper bound for overshoot or single-request Flare output.

November's previously observed five delivered images averaged about £0.065671 and eleven delivered text requests about £0.012338 each in the application ledger; these estimates exclude uncertainty, external charges and later activity, and are too small to predict customer demand. A largest application-quoted Flare request reserves £0.345576, but neither an already-dispatched call nor delayed provider charges have a documented numeric worst-case maximum. One concurrently in-flight image can still exceed its reservation and even the £2 contingency; text calls already in flight may add further expense, so actual total provider bills may exceed £30. The £24/£4/£2 proposal cannot guarantee paid-customer service and must remain inactive until supported by subscriber demand and founder-approved residual risk. No strict provider billing guarantee is claimed.

The adapted localhost-only PostgreSQL suite passed 14 scenarios with synthetic provider responses, including image concurrency, both sub-budget limits, text after image exhaustion, uncertainty, missing/invalid settings, monthly rollover and existing global limit/overrun accounting; the original suite's remote guard was not modified. The inherited test label `real Neon` in the output refers to a synthetic mock; actual connections were local. Policy/image unit tests, TypeScript and lint were also run separately. A standalone provider project, secret provisioning, in-flight cutoff behaviour, external alert delivery and production rollout are unverified.

**NOT READY:** assess subscriber demand and current provider billing, obtain founder acceptance of the specifically unquantified in-flight risk or a provable provider bound, and verify deployment/rollback and external monitoring before activation. If approved later, deploy only after review, verify every serving instance uses the same approved setting, check text/image separation and budget accounting on an isolated Preview, then monitor errors and provider spending; do not auto-merge or deploy. Remove the setting and roll back only with a reconciled view of outstanding requests; old versions retain the original shared-only budget and, after 19 November, rollback to the pre-PR build stops AI generation.
