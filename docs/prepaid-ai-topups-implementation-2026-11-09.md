## Implemented path and boundaries

- A server-owned catalog defines £5/25, £9/50 and £15/100; Checkout is authenticated, account-bound and gated, accepts a package and request ID but not a client price, creates a one-time test-mode Stripe Session, and persists its exact idempotent form. A global lock and partial unique index allow one pending attempt per account: another tab resumes the same package rather than creating another uncertain payment. An attempt with uncertain or lost Stripe identity is held for operator reconciliation, not silently retried with a new key.
- A signed test-mode webhook fetches the expanded Session and PaymentIntent server-side, checks identity, account, package amount, currency, quantity, mode, completion, payment status and charge, and inserts one credit grant in the same locked transaction. Delayed payment remains pending. Failed and expired sessions are closed only after fresh, conclusive Stripe evidence. Refund/dispute evidence is persisted even if received before issuance; duplicate and out-of-order events cannot issue a second grant.
- `0009_prepaid_text_credits.sql`, registered in the Drizzle journal, adds the purchase, reservation, append-only ledger, reversal inbox, reconciliation and alert records. Purchase/account foreign keys and unique grant/attempt constraints supplement application locks. Runtime privileges permit append-only ledger and reversal records. The transaction also reserves the existing global AI budget. Included credits are selected first; prepaid text credits are separately reserved, consumed or released. Monthly reset changes included usage only. Prepaid credits have no automatic expiry in the schema; **no non-expiry promise is approved**.
- Any refund, including partial, or dispute freezes the entire affected package pending review. In-flight reservations are voided before dispatch or delivery if the reversal has reached the application. Credits already consumed remain in the ledger and purchase history; no automatic debt collection, deductions from other purchases or reinstatement is performed. A provider request that finished before a delayed reversal cannot be undone. Webhook delay and outages leave an eventual-consistency window; the reconciliation worker limits but cannot eliminate that window. Founder policy and support procedures for partial refunds, consumed credits and won disputes remain necessary.
- The dashboard shows included and purchased balances, pending reservations, packages, purchase history and payment state. Studio can request a generation when purchased credits remain, but the server makes the actual decision. Stored prepaid credits can be used while an eligible paid membership is active; a canceled subscription does not delete them. Existing subscriptions, Founder entitlements, lifetime limits, images and the £30 spend ceiling are not changed.
- The administrator financial report separates prepaid delivered requests and estimated settled AI spending within each lifetime/subscription cohort. Token-based accounting is an estimate, not the provider invoice. The existing per-account cap remains opt-in and unset; this PR does not activate it. The application-level global cap cannot police independent provider-key usage.

## Reconciliation and alerts

Top-up jobs use persistent due times, expiring leases, eight attempts and bounded exponential backoff. Unresolved checkout identities and uncertain payments retain their records and eventually generate durable alerts; expired sessions are closed only when verified unpaid without a PaymentIntent. Paid records are rechecked for missed reversals. Stale credit holds are surfaced for review rather than automatically released. An admin-only endpoint exposes failures, alerts and stale holds; authenticated, same-origin administrator retry records an immutable reason and identity. Optional HTTPS alert delivery is retried until acknowledged for both top-up and lifetime alerts. No alert endpoint is configured by this work.

**Operational blocker:** the repository's existing Vercel cron runs once daily. A five-minute reschedule and 30-second backoff specify earliest eligible times, not guaranteed execution. An authorized scheduler with sufficient frequency, compatible Vercel plan/runtime, alert endpoint, delivery monitoring and operator runbook must be configured and independently tested. A lost session ID requires operator reconciliation; the worker does not search an unbounded Stripe history. The account-level spend limit remains inactive until founder approval. The cost policy expires 19 November 2026 UTC and must be re-reviewed before then.

**Preview isolation remains unverified:** `lib/db/client.ts` requires fixture mode in Vercel Preview. `lib/preview-fixtures.ts` now allows a Stripe key only with explicit `CONTENTOS_PREVIEW_STRIPE_TEST=1`, a test-key prefix, the existing exact isolated-branch/database checks and Preview environment; it still rejects live Stripe, OpenAI and email-provider keys. Unit tests cover those checks, but no actual Preview credentials, branch identity or Stripe account/mode were inspected. Independently prove the database is isolated and the webhook secret and key belong to the intended test account before enabling the test-only path. Local sandbox verification alone does not establish Preview isolation.

## Model pricing and maximum costs

Application code currently allows at most 128,000 serialized request bytes, reserves 4,096 input tokens of overhead and sets `max_output_tokens` to 24,000, with zero automatic SDK retries. At the conservative reserve of **132,096 input + 24,000 output tokens**, the existing policy assumes £1 per USD plus 20%; these figures are upper-bound planning estimates for one successful request, not invoice evidence. The input reserve is a byte-based estimate with an overhead allowance, not a provider-side hard input-token cap; an unexpected provider overrun is detected after the call and suspends admissions. Real invoices, calls outside the ledger, provider errors, taxes, images and retry/uncertainty costs need separate coverage.

Official standard per-million input/output rates: [GPT-5.2 $1.75/$14](https://developers.openai.com/api/docs/models/gpt-5.2), [GPT-4.1 mini $0.40/$1.60](https://developers.openai.com/api/docs/models/gpt-4.1-mini), [GPT-5.6 Luna $0.20/$1.20](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [GPT-6 Luna $0.10/$0.50](https://developers.openai.com/api/docs/models/gpt-6-luna). For Luna, the estimates conservatively use the default 30-minute cache-write rate of 1.25× input. GPT-4.1 mini is listed as deprecated. Actual production `OPENAI_MODEL` override was not inspected; GPT-5.2 is the code default and older evidence showed GPT-4.1.

The public [Stripe UK standard-card example](https://stripe.com/gb/pricing/local-payment-methods) is 1.5% + £0.20, with fee rounded upward to the next penny for this illustration; other methods and negotiated rates differ. At current GPT-5.2 bounds, the estimated package contributions after that fee and before tax/overheads are **−£12.30, −£25.37 and −£53.49**. To cover bounded AI cost and the example fee with a 25% margin on gross revenue would require at least **£23.44, £46.58 and £92.89**, respectively; these are not approved prices and are not a profitability guarantee. Luna's theoretical upper bounds fit within the proposed package prices and that example margin, but a subscription or long-term lifetime liability still needs recurring funding, and no model can be adopted on price alone.

An unimplemented candidate envelope of 32 KiB serialized input plus 4,096 input-token overhead and 4,096 output tokens would reserve about £0.0079872 per GPT-6 Luna request. It could make the packages cheaper to fulfil, but has not been checked against full multi-format outputs, provider overhead, quality or existing subscription commitments. It changes the current limits and model and therefore needs explicit founder approval after evaluation. At that candidate envelope, 50 generations are about £0.39936/month/customer, while the current full-bound GPT-6 Luna estimate is £1.71072/month/customer. Neither number includes images, failures or other costs.

For an illustrative existing base of 10 Free, 5 Lite, 3 recurring Creator and 1 Studio customers using all 480 text credits, plus 25, 50 or 100 lifetime customers each using 50, the total is 1,730 / 2,980 / 5,480 generations monthly. At current GPT-5.2 bounds this is **£1,177.44 / £2,028.19 / £3,729.70** before images and failures. At the unimplemented GPT-6 Luna candidate envelope it is **£13.82 / £23.80 / £43.77** respectively, again before images, uncertainty, VAT and overhead. The £30 budget cannot guarantee the current GPT-5.2 promise; protecting the entire incumbent £30 leaves zero funded lifetime sales under the existing gate. One-time top-up receipts do not increase the monthly spending ceiling.

## Representative quality evaluation

Using a separately funded project approved by the founder, the evaluation script sent synthetic milestone/giveaway, practical LinkedIn and limited-claim TikTok briefs through the actual GetContentOS prompt and output schema, with 1,800 output tokens and no retries. GPT-5.6 Luna completed three samples: **two passed** the application parser and the milestone sample was rejected by the existing grounding check. GPT-5.2 and GPT-6 Luna were denied by the project. GPT-4.1 mini initially rejected an unsupported reasoning parameter and, after correction, was also denied. Raw synthetic outputs and usage are in `docs/pr22-topup-model-evaluation-*.json`; the three successful calls reported 10,818 input and 751 output tokens. Approximate conservative Luna usage is £0.0044 under the stated assumptions; no provider invoice was obtained.

These three cases are too few to assess all formats, style, factual grounding, long inputs or consistency, and there is no direct baseline comparison. **No cheapest acceptable model can yet be recommended.** GPT-6 Luna is the least expensive published candidate compared here, but its availability and quality are untested. Expand the funded, blinded comparison with GPT-5.2 and candidate access, measure unsupported claims, schema/format fidelity, all platform outputs, latency, and repeatability, and obtain founder approval before changing routing or limits.
