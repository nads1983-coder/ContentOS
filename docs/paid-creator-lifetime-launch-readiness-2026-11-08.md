### Further application work / risks established by inspection

**A. The proposed manual reinstatement is not currently implementable safely by editing the profile.** `risk()` in `lib/paid-lifetime-fulfillment.ts` always returns historical refund/dispute/review evidence. Changing profile status alone leaves the purchase reversed; changing purchase status to completed causes a later reconciliation or webhook to apply the inbox risk again. Deleting inbox evidence to make restoration work is unacceptable. After founder policy approval, add an explicit authorized adjudication record/transition with actor, reason, Stripe evidence and timestamp, and rules distinguishing reviewed events from *new* reversals. New full refunds/disputes must still revoke access. Test replay, operator retry, concurrent reversal and reconciliation. This is a release prerequisite for promising reinstatement, not an automatic restoration feature approved by this review.

**B. Reconciliation needs a time-bounded, fair operational design.** In `lib/paid-lifetime-reconciliation.ts`, up to 50 recurring guards are processed before any lifetime row. That guard query has no ordering or rotation, so retained guards may monopolize selection. Each Stripe request can take 12 seconds (`lib/stripe-rest.ts`); lost-session recovery may list up to 100 pages. A function timeout can occur before lifetime rows are reached or before `finally` rotates a row. The daily schedule alone is not proof of timely repair. Before launch, implement and test a deadline/cursor or durable queued batches, fair guard rotation, bounded per-item work and alerts on incomplete sweeps. Do not solve this by expiring uncertain payments. A NULL-session recurring guard also currently requires manual resolution indefinitely.

**C. Environment separation is an external prerequisite, not enforced proof in the payment objects.** Validators verify amount, currency, stored session and account/purchase metadata, but do not explicitly enforce `livemode` or a configured Stripe account identity. Harden test harness/launch configuration with fail-closed expected-mode/account checks, and record sanitized verification evidence. Do not connect a Preview to a live key and assume the disabled UI is sufficient protection.

**D. Delayed failure semantics need actual Stripe evidence.** The async-failure handler accepts PI `requires_payment_method` as well as `canceled`, zero received and no paid charge. Do not infer from the name alone that a PI can never subsequently succeed; validate the complete Checkout lifecycle for each enabled delayed method. If a supported flow permits late success after release, the slot must remain held until an authoritative terminal condition. This is an unverified scenario, not a reproduced Stripe defect.

These concerns are not safely resolved by a cosmetic one-line change. No application patch is included: worker orchestration, environment policy and adjudication need targeted design/tests; reinstatement additionally needs founder approval. This report must not be read as claiming all application work is complete.

## 2. AI routing, cost and sustainability

Actual code: `app/api/generate/route.ts` selects `OPENAI_MODEL ?? "gpt-5.2"`; preview fixtures select GPT-4.1 and simulate usage. It uses Responses API structured output with the whole instructions/input/schema serialized into the cost quote. `GENERATION_LIMITS` sets 96,000 incoming request bytes, 24,000 maximum output tokens, 90-second timeout and zero automatic retries. `lib/ai-cost.ts` permits up to 128,000 serialized provider-payload bytes and bounds input tokens as bytes + 4,096. That byte bound is conservative, not measured typical token usage. No explicit reasoning-effort parameter is sent by this route.

The cost allowlist also supports GPT-4.1 and pinned aliases. Unknown models fail closed. GPT-5.2 accounting uses $1.75 input and $14 output per million tokens, treating cached input at the uncached rate; official cached input is $0.175. Prices checked against [OpenAI's model documentation](https://developers.openai.com/api/docs/models/gpt-5.2). Output accounting must include all billable output, including reasoning usage. The code converts conservatively at £1 per US$1 plus 20%, rounding upward to integer micro-pounds; this is a policy reserve, not an exchange-rate forecast.

The deployed environment's model override remains unverified. Historical GPT-4.1 ledger entries do not prove today's routing. `COST_POLICY` is still version `2026-10-21-v3`, expiring **19 November 2026 at 00:00 UTC**; new calls stop after expiry. Renew only after model/price/bounds verification and testing.

### Numerical exposure

| GPT-5.2: 2,000 + 1,000 (illustration) | £0.021000 | £1.050000 | £26.250000 |
| GPT-5.2: 2,000 + 3,000 (illustration) | £0.054600 | £2.730000 | £68.250000 |
| GPT-5.2: current reserve bound 132,096 + 24,000 | £0.680602 | £34.030100 | £850.752500 |
| GPT-4.1: same current reserve bound, code's $2/$8 rates | £0.547431 | £27.371550 | £684.288750 |

The £30 global budget is shared with existing text users, images, failures and uncertain requests. At the maximum GPT-5.2 quote, only **44** calls fit even in an otherwise empty £30 month (44 × £0.680602 = £29.946488). A first customer could be prevented from receiving the last six of their promised 50. The budget therefore controls admitted spending but does not fund delivery.

`commercial-ledger.ts` serializes shared monetary holds and checks London-month spend before reservation/dispatch, retains uncertain cost, settles only supported usage, suspends on bound violation and records £20/£25 alerts. It does not cap unrelated calls made with the same provider key/project outside this ledger. Alert records alone are not an on-call notification system. Failure attempts can consume money without consuming successful-generation allowance; zero SDK retries does not prevent new user attempts. Thus £850.75 is not a complete worst-case monthly business cost.

`lib/paid-lifetime-capacity.ts` protects the full £30 for incumbents and returns zero funded lifetime places. This is the correct current sales outcome. It is a closed gate, not a sustainable commercial implementation. Its hardcoded GPT-5.2 liability formula must be kept aligned with any future reviewed routing/bounds.

### Financially viable alternatives and their conditions

1. **Keep £30 and the approved delivery unchanged: do not sell yet.** With the full incumbent budget protected, incremental funded capacity is zero. This is the only immediately implementable option requiring no commercial or budget change.
2. **Fund a finite cohort from reliable recurring operating income, with founder-approved budget expansion.** For 25 customers at current successful-call bounds, protect £30 incumbents + £850.7525 cohort = £880.7525/month. A *planning* 25% cohort reserve adds £212.688125, totalling £1,093.440625/month (about £13,121.29/year), before hosting, tax, Stripe fees, support and refunds. A nominal £1,100 allocation is therefore only an AI planning example, not a proven sufficient budget. Failure/uncertainty admission limits and actual incumbent liabilities must be modeled explicitly. Sell only the funded number; each extra £149 customer creates another £34.0301/month successful-call liability at current bounds. This option is financially viable only with an evidenced ongoing subsidy and a reviewed sales ceiling; it is not authorized now.
3. **Retain GPT-5.2 and 50 generations but validate a materially smaller request envelope, then fund the resulting cohort.** For example, an enforced *total* input bound of 10,000 tokens and 2,000 output tokens gives £0.0546/call, £2.73/customer/month and £68.25 for 25. Protecting £30 incumbents plus a planning 25% cohort contingency gives £115.3125/month. This is a potential ~£120 AI envelope, not current code: the existing quote requires exactly 24,000 output tokens and its serialized schema/input may exceed that proposed input bound. Prove quality and all supported content formats before founder approval; do not silently truncate content, change model quality or take entitlements away. Keep a funded sales ceiling and retain monetary controls.
4. **Fixed £30 with a future proven low-cost delivery architecture and a small cohort is only conditional.** Illustratively allocating £10 incumbents + £5 failure reserve leaves £15 for lifetime. To support 25 × 50, total cost must be ≤£0.012/generation. The current maximum is ~57 times that. Such an allocation also changes today's protected-incumbent policy and may be insufficient for existing subscribers. Benchmarking, an enforced bound, incumbent demand proof and founder approval are mandatory. Caching/batching/routing can reduce average spend but are not assumed to preserve quality, interactivity or fresh output. No cheaper model substitution is approved here.

Raising the one-time price alone does not solve indefinite recurring obligations. Gross £99 covers only ~2.91 months at £34.0301/month; £149 covers ~4.38 months, before all other costs. Even at the £1.05 illustrative average, £99 covers ~94.3 months, not perpetuity. Do not rely on later lifetime sales to fund earlier customers. Define service-lifetime terms transparently and have the founder approve the economic obligation, refund terms and any total-sales ceiling.

## 3. Refund and dispute policy decisions

Recommended default is consistent quarantine, followed by a time-bounded human review—not permanent unexplained loss of access and not automatic restoration.

- Full refund: revoke only this paid lifetime entitlement; preserve history and all unrelated subscriptions/legacy rights. Never restore it on success replay.
- Partial refund: founder must specify whether it is a goodwill adjustment retaining the full 50/0 product, or a cancellation settlement. Recommended goodwill outcome is restoration of the same original benefits after authorized review, no new early-bird allocation and no quota reset. Require verified total refunded/captured amounts, no other unresolved risk and documented reason. Other cases stay suspended pending resolution; do not invent a proportionate generation allowance.
- Won dispute: recommend restoring the original purchase after an authorized reviewer verifies the final won outcome, captured payment, refund history and absence of other unresolved disputes. “Closed” alone is insufficient. Lost/open disputes remain suspended. Handle repeat disputes and later refunds as new evidence.
- Founder must approve review owner, service-level target, customer communications, repurchase policy, treatment of interrupted months and any credit/remedy. Retaining historical early-bird places after refunds is the present behaviour; it needs to match “eligible customer” and public terms.

Implement the adjudication mechanism described in finding A before promising restoration. It must preserve inbox evidence and remain effective under worker/replay processing. No automatic reinstatement, quota reset or production manual edit is approved by this review.
