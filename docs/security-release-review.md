### S1 [P1] Failed text attempts bypass any durable attempt-rate budget

**Introduced with the new text reservation path.** Monthly accounting counts successful usage and currently pending reservations, but failure removes the pending charge without incrementing an attempt budget. A new request ID is then admitted immediately. The concurrency ceiling does not constrain sequential attempts, and Better Auth's limiter does not wrap this application endpoint.

Evidence: [reserveGenerationInProfile](/tmp/contentos-ai-first/lib/generation-reservation.ts:160) checks only duplicates, concurrent reservations, and successful/pending monthly usage at lines 160-169; [failGenerationInProfile](/tmp/contentos-ai-first/lib/generation-reservation.ts:204) makes the attempt terminal without accounting for attempted work. [The route](/tmp/contentos-ai-first/app/api/generate/route.ts:115) forwards client cancellation to the provider and runs the failure transition at lines 124-144. [Terminal retention](/tmp/contentos-ai-first/lib/generation-reservation.ts:116) keeps failed-request hashes indefinitely, so repeated failures also grow the profile document.

Impact: an authenticated account can repeatedly start work that fails, times out, or is cancelled, using new IDs without exhausting the successful-generation allowance. Provider cancellation does not establish that no billable work occurred. Repeated attempts consume application/provider resources and grow tombstones even if no result is returned. This is a resource-abuse gap, not evidence that failed content should be charged as a successful generation.

Validation: an in-memory execution of the actual reservation functions admitted **25 sequential failed attempts** on the same synthetic free account at the same timestamp: successful usage remained **0**, with **24 terminal hashes** and the latest failed record. No provider/DB request was made.

Bounded fix: add an atomic per-account short-window attempt budget before provider dispatch, separate from monthly successful credits. Consume it for every newly admitted attempt, including later failures/aborts; replay/status checks must not consume another attempt. Return 429 with Retry-After. Retain the existing terminal-ID protection; do not simply delete tombstones and make old requests executable again. An attempt cap bounds adversarial growth while a future ledger-storage change can address long-term retention.

Acceptance: concurrent and sequential new-ID attempts hit the same durable cap across instances; failed work leaves customer success credits unchanged; completed-ID replay remains free; another account's budget is independent.

### S2 [P1] Image generation can exceed quota through concurrent requests and unrecorded successes

**Inherited path; PR3 adds the account-header guard but not atomic image admission.** [Image quota checking](/tmp/contentos-ai-first/app/api/generate-image/route.ts:133) reads usage before provider work. [Provider dispatch](/tmp/contentos-ai-first/app/api/generate-image/route.ts:217) happens before any reservation. [Usage recording](/tmp/contentos-ai-first/app/api/generate-image/route.ts:286) runs afterward, and its failure is swallowed before returning success. The [repository event writer](/tmp/contentos-ai-first/lib/postgres-repository.ts:96) locks only the eventual append, not admission.

Impact: two requests reading usage 99 both pass a 100-image allowance and can both incur image-generation cost. Larger concurrent bursts have the same problem. A failed usage write can also return a usable image without accounting for it. The new account header does not prevent abuse by the correctly authenticated account.

Validation: the actual image route was evaluated with synthetic auth/storage/image-renderer mocks and a two-reader barrier. Both requests returned **200**, taking fixture usage **99 -> 101**. Provider calls were disabled; **zero network calls** occurred. This proves the route's check/use race, not live provider behavior.

Bounded fix: give images an atomic per-account reservation, idempotency key, and image-specific usage counter before provider work, reusing the text ledger's transaction pattern without merging the two product allowances. Complete accounting before acknowledging success; preserve an uncertain reservation on ambiguous writes. Apply timeout/abort handling and the attempt budget separately from successful credits. Keep template-fallback charging semantics explicit rather than changing entitlements incidentally.

Acceptance: at usage 99, two concurrent reservations permit exactly one new image job; repeat IDs do not dispatch twice; a completion-write failure does not return an untracked 200; both existing lifetime sources retain their intended limits.

### S3 [P1] A reset metadata-hook error skips session revocation after changing the password

**Inherited authentication behavior confirmed against installed Better Auth 1.7.4.** [onPasswordReset](/tmp/contentos-ai-first/lib/auth-config.ts:22) executes a separate SQL update that can throw. The installed [reset endpoint](/tmp/contentos-ai-first/node_modules/better-auth/dist/api/routes/password.mjs:156) consumes the reset token, writes the new password, awaits that hook, and only then deletes user sessions (lines 156-171). These steps are not wrapped in one reset transaction. Setting `revokeSessionsOnPasswordReset: true` therefore does not guarantee revocation when the application hook fails.

Impact: a transient failure of the verification/legacy-flag update returns an error after the password has changed and the token has been consumed, while previously issued sessions remain valid. This matters when resetting a password to recover from a compromised session. [getCurrentUser](/tmp/contentos-ai-first/lib/auth.ts:6) checks account verification/disable state, not a password-change/session-revocation epoch.

Validation: the installed reset handler was executed in memory with mocked adapters and a throwing metadata hook. Result: **passwordUpdated=true; sessionsRevoked=false; outcome=error**. No real account, token, password hash, or DB was used.

Bounded fix: make session invalidation independent of this optional metadata update. The smallest mitigation is explicitly revoking sessions before the flag update in the reset hook, retaining the library setting as defense in depth; do not swallow revocation failures and claim success. For full failure atomicity, use a reviewed transaction-aware reset path that commits credential mutation, verification flags, token consumption, and session deletion together. Do not disable email verification or revive disabled accounts as a workaround. The small mitigation fixes the demonstrated skipped-revocation path but does not make all DB-outage cases atomic.

Acceptance: inject a flag-update failure after password mutation and verify old sessions cannot authenticate; also inject revocation/storage failure and ensure no false-success response. Test concurrent token reuse, an expired token, migrated accounts without credential rows, and disabled accounts.

### S4 [P1] Stale subscription-deletion events overwrite newer subscriptions; signatures never expire

**Inherited billing integrity defect, with a related replay weakness.** [Subscription deletion handling](/tmp/contentos-ai-first/app/api/billing/webhook/route.ts:227) takes the deletion snapshot directly rather than retrieving current customer entitlement. [updateSubscriptionStatus](/tmp/contentos-ai-first/lib/postgres-repository.ts:138) applies it to the matched profile without comparing the incoming subscription ID to the profile's current subscription or a last-processed event. Thus a delayed deletion for subscription A can replace an active subscription B with Free/canceled and A's ID.

Separately, [verifyStripeSignature](/tmp/contentos-ai-first/lib/stripe-rest.ts:727) verifies an HMAC but never checks the timestamp's age. [The webhook event shape/handler](/tmp/contentos-ai-first/app/api/billing/webhook/route.ts:26) does not track event ID/creation time or deduplicate ordinary subscription events. A captured authentic signed payload can therefore be replayed indefinitely. Exploiting the signature weakness requires possession of a valid prior payload/signature; it is **not** a signature-forgery or unauthenticated arbitrary-entitlement claim. The stale-event bug can occur through legitimate delayed delivery without an attacker.

Validation: the actual signature verifier accepted a synthetic correctly signed payload with timestamp **1**. A dummy signing key was supplied entirely in memory. No real webhook secret or event was read. The stale-subscription overwrite is established from the route/repository control flow; its DB integration scenario remains for the main agent.

Bounded fix: enforce a documented signature timestamp tolerance (for example 300 seconds), reject malformed/excessively future timestamps, and verify any valid v1 signature during secret rotation rather than collapsing duplicate header keys. Add durable event-ID idempotency. Under the same profile mutation lock, ignore deletion of a non-current subscription or reconcile the customer's current subscription before writing. Event-ID deduplication alone does not solve differently identified out-of-order events. Keep the lifetime guard in that same lock.

Acceptance: reject old/malformed signatures; accept a fresh signature and valid rotated signatures; process duplicate events once; deliver A's deletion after B's activation and preserve B; exercise both event orders. Founder and manual lifetime fixtures must remain unchanged throughout.

Primary reference: Stripe recommends duplicate-event tracking and signature verification in [Manage webhook endpoints](https://docs.stripe.com/events/manage-webhook-endpoints), and warns that snapshot data can be stale before critical actions in [Set up events](https://docs.stripe.com/events/set-up-events). Accessed 2026-10-18. No Stripe account/API calls were made.

### S5 [P2] Signup's before hook acquires a second connection while its transaction holds one

**Inherited; source-confirmed concurrency/availability hazard, not DB-load-tested here.** [Auth configuration](/tmp/contentos-ai-first/lib/auth-config.ts:19) enables adapter transactions. Its [user-create before hook](/tmp/contentos-ai-first/lib/auth-config.ts:31) uses `getPool().query`, which needs a separate connection. [The shared pool](/tmp/contentos-ai-first/lib/db/client.ts:9) has maximum size 3 and a 15-second connection acquisition timeout. Installed [sign-up](/tmp/contentos-ai-first/node_modules/better-auth/dist/api/routes/sign-up.mjs:143) holds an adapter transaction through hashing and user creation; the [Drizzle adapter](/tmp/contentos-ai-first/node_modules/@better-auth/drizzle-adapter/dist/index.mjs:556) implements this with a DB transaction connection.

Impact: when three signup transactions acquire the pool connections before reaching their before hooks, all three wait for a fourth connection that cannot be released until one request times out. This can occur in a legitimate burst within the configured five-signups-per-hour IP allowance. Other auth/storage operations sharing the process pool are delayed too. It is bounded by timeout, not a permanent database deadlock.

Bounded fix: run the reserved-profile lookup through the active transaction connection/adapter instead of checking out another pool connection. Keep the reserved-email safeguard and unique constraints. If that requires a small adapter extension, scope it to this lookup; merely increasing pool size postpones the same saturation pattern. Do not disable transactions.

Acceptance: in an isolated DB with pool size 3, synchronize three new-account signups immediately before this hook and confirm all complete without pool-acquisition timeout; verify orphaned legacy profiles still cannot be claimed through signup and rollback leaves no partial credential account.

Origin is a browser-CSRF control, not a bot/rate-limit boundary.
